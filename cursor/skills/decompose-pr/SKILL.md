# Decompose PR

Split one large branch (the **source branch**) into a stack of smaller branches. Each branch is based on the one before it, so they can be opened as stacked PRs. Losing no logic from the source branch matters more than anything else.

You need the repository path, the source branch, and its base branch. If any of them is missing, ask for it.

## Size rule

Count the LOC of each branch as added plus deleted lines against its parent (`git diff --numstat <parent>...<branch>`). Leave out lock files, autogenerated migrations, and binary files.

- Target: as small as a coherent change allows, at most **500 LOC**.
- Hard limit: **1000 LOC**. Only exceed it when a single indivisible change (for example, one generated file or one large migration that cannot be split) is bigger than that. Report each such case explicitly.

## Safety rules

- **Never modify the source branch.** Do not commit to it, rebase it, reset it, or amend its commits.
- **Back up before you start**: `git branch backup/<source-branch>-<YYYYMMDD-HHMM> <source-branch>`. Keep the backup ref; never delete it.
- Start from a clean working tree. If there are uncommitted changes, stop and report them.
- Never force-push and never push at all. Pushing is the caller's job.
- Do not change the code while splitting: no refactoring, renaming, reformatting, or fixing. The only exception is the minimal glue a branch needs to build on its own (see step 4). Report all such glue.

## Steps

1. **Understand the change**: read `git log <base>..<source>` and `git diff <base>...<source>`. List the logical pieces of the change and the dependencies between them (e.g. model → service → API → UI, or refactoring → feature → tests).
2. **Plan the stack**: order the pieces so every branch depends only on branches below it in the stack. Keep tests with the code they test. Put lock files and generated migrations in the same branch as the change that needs them. Name the branches `<source>-1-<slug>`, `<source>-2-<slug>`, and so on. Check each planned branch against the size rule.
3. **Build each branch**, in order:
   - Create it from its parent (the base branch for the first one, the previous branch after that): `git switch -c <name> <parent>`.
   - Bring over its part of the change from the source branch. Use `git checkout <source> -- <paths>` for whole files. For partial files, write a patch (`git diff <branch> <source> -- <path> > /tmp/part.patch`), keep only the hunks for this branch, and `git apply` it. Avoid interactive commands such as `git checkout -p` or `git add -p`. Cherry-pick source commits when they already match a piece exactly.
   - Commit in small, atomic commits that follow the repo's commit style.
4. **Verify each branch**: run the project's linters and tests (see `AGENTS.md`, `.cursor/rules/`, the `Makefile`, `lets.yaml`, or `package.json`). If a branch fails because it references code from a later branch, move that code down into this branch or reorder the plan. If that is impossible, add the minimal glue and record it. Record the result per branch.
5. **Check equivalence**: the last branch in the stack must match the source branch exactly.
   ```bash
   git diff <last-branch> <source> --stat
   ```
   The output must be empty. If it is not, the missing or extra changes belong in the stack: fix the right branch (and rebuild the branches above it) until the diff is empty. Do not report success while the diff is non-empty. Any glue from step 4 must also be gone by the last branch.
6. **Check the stack**: for every branch, confirm `git merge-base --is-ancestor <parent> <branch>` succeeds, and recount its LOC against its parent.

## Report

Return exactly this:

1. **Source**: source branch, base branch, and backup ref.
2. **Stack**: a table in stack order with columns: branch, parent, LOC, summary of what it changes (a sentence or two, no file-by-file lists), lint/test result.
3. **Equivalence**: the command you ran for step 5 and confirmation that its output was empty.
4. **Notes**: any branch over 500 LOC and why, any branch over 1000 LOC and why it cannot be split, any glue added, and anything left for the user to decide.
