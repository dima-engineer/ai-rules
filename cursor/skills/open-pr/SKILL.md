# Open PR

Push the current changes and open a pull request (PR). Use any extra context the user gave in their message (base branch, ticket, reviewers).

## Steps

1. **Tooling**: use the GitHub CLI (`gh`) or a configured GitHub MCP server. If neither is available, stop and ask the user to set one up (for MCP: Cursor **Customize** → MCP, or `mcp.json`).
2. **Branch**: run `git branch --show-current`. If it is `main` or `master`, stop and ask the user to switch to a feature branch.
3. **State**: run `git status --short` and `git log --oneline -10` in parallel to see what is uncommitted and what commit style the repo uses.
4. **Checks**: run the project's linters and tests. Look for commands in `AGENTS.md`, `.cursor/rules/`, the `Makefile`, `lets.yaml`, or `package.json`. Fix failures before continuing.
5. **Commit**: if there are uncommitted changes, review them with `git diff` and commit with concise messages that follow the repo's commit style. Keep every commit small, atomic, and independent: one logical change per commit that stands on its own. Never commit secrets or unrelated files.
6. **Size**: measure the PR size as described in [PR size limit](#pr-size-limit). If it is over the hard limit, follow that section before going any further.
7. **Push**: push the branch to GitHub, setting the upstream if needed. Never force-push.
8. **Draft**: review all changes on the branch against its base (`git diff <base>...HEAD`, `git log <base>..HEAD`) and draft a PR title and description. If a `PR_TEMPLATE.md` file exists in this skill's directory (next to this `SKILL.md`), follow it: it either is the template or says where to get one. Show the draft to the user. **Do not open the PR until the user approves it.**
9. **Open**: after approval, create the PR with `gh pr create` using the approved text.
10. **Report**: give the user the PR link.

## PR size limit

Smaller PRs are better. Even a large feature should stay at or under **500 LOC**. **1000 LOC is the hard limit.**

**How to measure**: run `git diff --numstat <base>...HEAD` and add up the added and deleted lines. Leave out:
- Lock files (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `Cargo.lock`, `Gemfile.lock`, `composer.lock`, `go.sum`, and similar).
- Autogenerated migrations, i.e. migration files produced by a tool (Django, Alembic, Prisma, etc.) and not hand-edited. Hand-written data migrations count.
- Binary files (shown as `-` in `--numstat`).

Tell the user the counted LOC and what you left out.

**Up to 1000 LOC**: continue. If it is over 500, mention that in the draft step.

**Over 1000 LOC**: do not push and do not open the PR. Ask the user with the ask questions tool, giving the counted LOC and these two options:
1. **Open the large PR anyway**: continue from the Push step.
2. **Decompose into stacked PRs**: follow [Decomposing into stacked PRs](#decomposing-into-stacked-prs).

## Decomposing into stacked PRs

1. **Delegate**: start a general-purpose subagent (Task tool) to do the split. Its prompt must include:
   - The repository path, the branch name, and the base branch.
   - The counted LOC and the files excluded from the count.
   - An instruction to read and follow the `decompose-pr` skill, with the absolute path of its `SKILL.md` (in the `decompose-pr` directory next to this skill's directory). That skill is only loaded when invoked explicitly, so the subagent must read the file.
   - An instruction to report back: the backup ref, the new branches in stack order with each branch's parent, LOC count, and summary of changes, the lint and test results per branch, and the result of the final equivalence check.
2. **Check the report**: confirm the subagent reported that the last branch in the stack matches the original branch exactly (an empty `git diff`). If it did not, or a branch is still over 1000 LOC, show the problem to the user and stop.
3. **Draft**: write one PR draft per branch, in stack order. Each draft has:
   - The branch name and its base: the first PR targets the original base, every other PR targets the previous branch in the stack.
   - Its LOC count.
   - A title and description written as in the Draft step (use `PR_TEMPLATE.md` if it exists). Say in the description where the PR sits in the stack, e.g. "Part 2 of 4, based on `<previous branch>`".

   Show all the drafts to the user. **Do not push or open anything until the user approves them.**
4. **Open**: after approval, push every branch in the stack (never force-push) and open the PRs in stack order with `gh pr create --base <parent> --head <branch>`. Once a PR exists, link it by number from the next PR's description.
5. **Report**: give the user every PR link in stack order and the backup ref of the original branch.
